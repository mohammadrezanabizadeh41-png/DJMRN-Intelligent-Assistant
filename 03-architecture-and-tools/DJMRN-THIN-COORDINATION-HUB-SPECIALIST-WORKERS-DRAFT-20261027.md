# DJMRN — هسته ارتباطی سبک و واحدهای تخصصی مستقل

**شناسه پژوهش:** DJMRN-THIN-COORDINATION-HUB-004
**تاریخ:** 2026-10-27
**وضعیت:** پیش‌نویس اصلاحی معماری بر اساس توضیح تازه کاربر — NOT APPROVED / NOT IMPLEMENTED
**هدف:** اصلاح برداشت «ایجنت مرکزی هوشمند سنگین و دائماً فعال». حفظ پروفایل استانداردهای ترکیبی v0.1 در همین پوشه و حفظ تصمیم‌های پیشین پروژه.

## ۱. نیاز دقیق کاربر

کاربر یک **هسته ارتباط، ثبت، کنترل دسترسی و هماهنگی سبک** می‌خواهد؛ نه دستیار یا Agent مرکزی که همه کارها را خودش تحلیل و اجرا کند. همه واحدهای تخصصی (پژوهش وب، ایمیل، تحلیل Python، دانشنامه، اسناد، بازبینی و غیره) باید درخواست‌ها/نتیجه‌ها/وضعیت‌ها را از طریق هسته قابل ردیابی کنند. واحدهای تخصصی می‌توانند جداگانه اجرا شوند، خطا و ادامه کار مخصوص خود را مدیریت کنند و تنها هنگام نیاز منابع مصرف کنند. جست‌وجوی عمومی وب به یک واحد Search مشخص واگذار شود و هر دستیار اختیار مستقل سرچ نداشته باشد.

## ۲. نقش هسته سبک

- API ورودی، ثبت درخواست، تخصیص شناسه معتبر Task/Message/Correlation و Parent ID
- دفتر پیام‌های بین واحدها، وضعیت تحویل، پاسخ، خطا و نتیجه (Durable Mailbox)
- Registry نام‌ها، قابلیت‌ها، مقصد مناسب، مالک عملیات و قواعد دسترسی
- کنترل اجازه کاربر و Agent برای انجام هر قابلیت روی منابع مشخص
- مسیریابی قطعی/قاعده‌مند قبل از هر فراخوانی مدل
- ثبت تاریخچه اجرا، شواهد و منبع؛ پیوند خروجی به درخواست‌کننده
- دریافت/واگذاری درخواست به واحد دانشنامه و تصمیم درباره اعلان‌های مرتبط بر اساس قواعد، مخاطبان مجاز و کیفیت منبع
- **اختیاری و فقط هنگام ابهام:** درخواست ارزیابی از Supervisor Agent یا Reviewer؛ مدل زبانی نباید همیشه فعال یا صاحب مجوز نهایی باشد.

هیچ کدام از این نقش‌ها الزاماً یک سرویس مستقل یا مدل جدا نیست. در P0 یک پروسه سبک + SQLite و توابع تخصصی درون همان پروسه یا زیرفرایند هنگام نیاز می‌تواند کفایت کند.

## ۳. توزیع مسئولیت

**Knowledge Steward / دانشنامه:** پاسخ جستجوی دانش تأییدشده، منبع معتبر، نسخه، زمان، شاخص تازگی؛ ثبت دانش جدید فقط پس از ارزیابی/تأیید. مکان منبع اصلی می‌تواند GitHub، Notion یا فایل مورد اعتماد باشد. هسته فقط متادیتا، مجوز و لینک را به‌شکل متمرکز نگه می‌دارد، نه نسخه کامل هر ایمیل و هر سند.

**Search Worker / پژوهش وب:** تنها واحد دارای مجوز و ابزار جست‌وجوی عمومی وب. دریافت Task با scope، محدودیت، بودجه، deadline؛ بررسی دانش موجود؛ جست‌وجو، واکشی مجاز، استخراج، ارزیابی، حذف تکرار و ارائه نتیجه همراه با منبع. ثبت تمام گام‌ها و خطاها در Workflow، retry محدود و backoff برای خطای گذرا، توقف روی دسترسی غیرمجاز، پایان با شکست مستند یا خروجی مستند؛ هیچ حلقه بی‌نهایت یا ساخت منبع جعلی. گزارش نهایی به درخواست‌کننده از طریق هسته برمی‌گردد. گزارش اجرای Search با دانش پذیرفته‌شده یکسان نیست.

**Email Worker:** مجوز خواندن محدود Gmail، تحلیل یا برچسب‌گذاری با ابزار Python؛ درخواست پژوهش بیرونی از Search Worker فقط از طریق هسته؛ ارسال به بیرون مستلزم تأیید صریح همان اقدام. کلید و توکن سرویس در دسترس دیگر نقش‌ها نیست.

**Document Worker:** اتصال به CAP-006 فعلی با کنترل فهرست فایل؛ شناسه اثرانگشت تکرارپذیر CAP-006 با شناسه واقعی و پایدار Task اشتباه نشود.

**Reviewer:** بررسی مستندات/نتایج به صورت درخواستی؛ مستقل‌بودن شخصیت منطقی، الزاماً مدل/فرایند دائماً ساکن نیست.

## ۴. ترتیب دانش‌محور به صورت مشروط

۱) درخواست به هسته می‌رسد؛ تشخیص capability، نقش درخواست‌کننده، سطح دسترسی و تازگی مورد نیاز.
۲) اگر مسئله به دانسته‌های پروژه نیاز دارد، به Knowledge Worker درخواست scoped lookup بده. «اول دانشنامه» یک سیاست وابسته به نوع کار است؛ هر پیام ساده را بی‌دلیل جستجو نکن.
۳) اگر پاسخ معتبر، مرتبط و تازه کفایت دارد، بازاستفاده شود؛ اگر ناقص/قدیمی است، وظیفه تخصصی WebSearch/Email/Code ایجاد شود.
۴) خروجی با شناسه منبع/شواهد ثبت و به درخواست‌کننده بازگردد.
۵) نتیجه برای استفاده آینده به واحد دانشنامه پیشنهاد شود؛ **ثبت log ≠ تأیید دانش**. اعلان به نقش‌های مشترک فقط بر اساس قواعد اشتراک، ارتباط و مجوز؛ نه انتشار خودکار محتوای محرمانه.

## ۵. یک پاکت پیام سبک، نه پروتکل نو

تعریف داخلی به وسیله JSON Schema/Pydantic و نگاشت استانداردها:
- message_id، task_id، correlation_id، parent_task_id، sender_role، requested_capability، recipient_id یا dispatch_rule، resource_refs، permission_context_ref، payload_ref، trace_id، reply_to، idempotency_key، created_at، deadline، schema_version.
- متن ایمیل خصوصی، اطلاعات محرمانه، کلیدها و محتوای حجیم در پیام تکرار نشود؛ reference همراه با ACL منتقل شود.
- Agnostic adapter: MCP فقط برای ابزار و منابع؛ A2A برای دستیارهای واقعاً مستقل در مرز سرویس؛ AG-UI برای رابط گفتگو؛ OpenAPI برای API عمومی/داخلی؛ PROV برای منشأ و شواهد؛ CloudEvents برای رویدادهای مستقل اگر روزی لازم شد.
- هسته Task اصلی را در ledger نگه دارد. وضعیت‌های RECEIVED, VALIDATED, QUEUED, RUNNING, RETRY_WAIT, WAITING_APPROVAL, SUCCEEDED, FAILED, CANCELLED, UNKNOWN_OUTCOME. یک مالک نهایی وضعیت هر Task، نه دو موتور مستقل که همزمان آن را تمام‌شده اعلام کنند.
- بررسی مجوز باید در هسته و محل اجرای ابزار انجام شود؛ متن Agent مجوز نمی‌سازد.

## ۶. نمونه گردش کار واقعی

کاربر: «ایمیل‌های کاری مرتبط را بررسی و پیشنهاد پیگیری تهیه کن».
Persian UI -> Hub ثبت Task -> Knowledge lookup معیارهای سابق -> Email Worker خواندن محدود -> Python analysis -> در صورت نیاز Search Worker با Workflow قابل بازیابی -> Reviewer اختیاری -> نتیجه به Email Worker و کاربر، همگی از طریق Hub -> Draft و Approval جداگانه پیش از ارسال -> log و پیشنهاد گزینشی دانش قابل‌استفاده آینده.

Search Worker نمونه: QUEUED -> RUNNING -> خطای timeout/rate-limit -> ثبت attempt و Retry-After/backoff -> retry محدود -> SUCCEEDED با source URLs و excerpt قانونی یا FAILED با علت -> ارسال به درخواست‌کننده؛ وضعیت و شواهد باقی می‌مانند، بدون retry بی‌پایان.

## ۷. مصرف منابع و توسعه

- برای 8GB Windows: یک هسته محلی سبک، یک SQLite فایل به عنوان پایگاه عملیاتی با بخش‌بندی منطقی؛ بدون Redis/Kafka/Dapr/Orleans، بدون مدل یا Python Agent جداگانه دائماً روشن برای هر نقش.
- به‌جای فراخوانی مدل برای هر پیام، deterministic dispatch و Worker عادی؛ مدل‌ها فقط برای reasoning/review در شرایط واقعی.
- اجرای سنگین ابتدا ترتیبی، محدودیت RAM/Timeout/Quota و امکان لغو.
- SQLite WAL خواندن همزمان دارد اما در هر لحظه تنها یک writer؛ برای چند رایانه و بار واقعی بالا باید storage و transport مستقل را بعداً بررسی کرد.
- DBOS از SQLite در اجرای محلی و ذخیره مراحل پشتیبانی می‌کند؛ فقط بعد از نیاز واقعی recovery آن را بسنجیم تا دو موتور authoritative retry مستقل نداشته باشیم.

## ۸. سناریوهای پذیرش

- یک درخواست از Agent A به Search Worker تنها از طریق Hub؛ source-linked result و trace به A برگردد.
- Agent فاقد مجوز نتواند مستقیم وب جستجو یا Gmail بخواند؛ DENIED پیش از اقدام.
- خطای جست‌وجو ضبط، retry محدود و restart بررسی شود.
- Knowledge شامل منابع تأییدنشده به‌عنوان دانش رسمی نشود.
- اعلان مرتبط فقط به گیرندگان مجاز ارسال شود.
- سیستم بدون LLM برای درخواست صرفاً قطعی کار کند؛ کارایی/RAM/زمان واقعی اندازه‌گیری شود.
- تعویض Runtime Agent، شناسه Task و شواهد را خراب نکند.
