## 2. Findings which materially change or sharpen the previous roadmap

**F01 — Build a thin *trusted capability-and-policy seam*, not a mandatory permanent core daemon.** A shared schema/codebase and host-specific adapters can be started on demand. A centrally running server is optional; the need for a queue, interprocess RPC, concurrent workers or separate state DB must be demonstrated. The UI/LLM chooses *suggested* intent, not filesystem roots, user identity, approval, spend, or tool authorization. The executable checks canonical allowlists and typed arguments immediately before doing work.

**F02 — Treat approval, external side effects and recovery as one contract.** For an email/send/post/payment: task ID + target + payload hash + user approval bound to that exact action + durable idempotency key + state machine (`PENDING → APPROVED → ATTEMPTED → CONFIRMED`; `UNKNOWN_OUTCOME` checked externally, never blind resend). Checkpoint libraries alone cannot guarantee exactly-once delivery across untrusted external providers. Workflows, model prompts and UI buttons cannot bypass the execution-side policy boundary.

**F03 — Treat host/UI, deterministic tool, inference model, workflow runtime, operational state and knowledge search as six distinct roles.** They may live in one process at first. Do not conflate an Agent chat UI with a model engine, an MCP transport with permission enforcement, a Notion research index with execution state, or RAM used by model weights with RAM used by the host/browser/context.

**F04 — A ready-to-use workflow engine has become a credible *later* alternative, not an immediate prerequisite.** Official current Dagu README documents Windows single binary, on-device GUI, retries, scheduling, human tasks, MCP and no external message broker/DB server. **But:** execution can launch shell/subprocesses; Dagu is not an OS security sandbox, provider-grade permissions for this specific use are unverified, and its own long-running process consumes resources. [Primary Dagu source](https://github.com/dagucloud/dagu/blob/main/README.md). Compare when real multi-step unattended work exists, with direct script, Windows Task Scheduler, DBOS and LangGraph, not merely feature lists.

**F05 — Durable-workflow families are different, not interchangeable.** [DBOS Python programming guide](https://docs.dbos.dev/python/programming-guide) documents step/workflow recovery and SQLite default; [DBOS database guide](https://docs.dbos.dev/python/tutorials/database-connection) recommends PostgreSQL for distributed production. An [older/general architecture page](https://docs.dbos.dev/architecture) frames PostgreSQL as core: **documentation scope/age varies; validate exact version and production mode before ranking**. [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence) distinguishes per-thread checkpointer from cross-thread Store; [interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts) resume graph nodes, requiring careful handling of replay and writes. Dagu focuses on external-script workflow operations. None by itself solves policy, ambiguous send, global RAM admission or Windows child-process cleanup. DBOS for durable code workflows; LangGraph for adaptive model graphs; Dagu for script/runbook schedules; start without any for a single request→tool→response.

**F06 — Prefer available model lifecycle primitives before new model router.** [LM Studio TTL/Auto-Evict](https://lmstudio.ai/docs/developer/core/ttl-and-auto-evict) applies specifically to JIT-loaded models; manually loaded models can stay resident. [LM Studio server settings](https://lmstudio.ai/docs/developer/core/server/settings) describes opt-in MCP and authentication/network controls. [llama.cpp server docs](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md) documents disabled-by-default `--sleep-idle-seconds`. No claim of actual working-set reduction on user's Windows until measured idle/loaded/unloaded states. Future external routers (llama-swap/LiteLLM) only if the simpler controls fail a measured need.

**F07 — Local chat host choice is not settled.** [Jan Desktop MCP](https://docs.jan.ai/desktop/mcp) describes tool-call approval and an optional **global Allow All**, plus model-specific unreliable tool use. [Jan Agent](https://docs.jan.ai/agent/permissions) documents plain terminal `jan` auto-approving calls by default; `jan --safe` and `--sandbox` are **separate protections**. Thus Jan Agent is not equivalent to a safe preconfigured desktop UI. [Open WebUI MCP](https://docs.openwebui.com/features/extensibility/mcp/) requires v0.6.31+ and **native Streamable HTTP**, not native local stdio; adapting stdio via mcpo adds a proxy surface and cost. Its built-in Python extensions execute on server, potentially sharing CPU/RAM and trust domain. These options are host-specific and conditional, not selected. A lightweight local chat facade plus typed tool bridge remains a genuinely independent greenfield comparator.

**F08 — MCP is interoperability, NOT a security boundary.** Current [MCP security practices (2026-07-28)](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices) cover confused deputy, token passthrough, SSRF, local-server and stdio proxy risks, scope minimization. Apply allowlisted tool definitions, separate read/write capabilities, fixed roots, no arbitrary shell/network, bounded execution, validate tool input and approval at actual executor. No automation based on untrusted email/README/workflow JSON instructions.

**F09 — Windows can constrain process trees, but verification is necessary.** [Microsoft Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) manages process groups, resource limits and termination. This is a candidate primitive for later owned-process supervision, **not proof** that existing Windows model engines or browser sessions are under one supervisor. Job Objects do not themselves provide tool policy or durable receipts; request real Windows tests only when warranted.

**F10 — Search/index should be a rebuildable projection, not a second authority.** [SQLite FTS5](https://www.sqlite.org/fts5.html) offers Unicode61 and ranking; its default tokenization does not promise Persian morphological recall or normalization for ی/ي, ک/ك and ZWNJ. Start with CAP-006 + live GitHub/Notion sources and provenance, add bounded index after 20–50 documents/queries indicate value, test Persian normalization with original evidence unmodified. Index/state backup, source freshness and hash policies are separate. Avoid importing entire Notion libraries into a parallel canonical DB.

**F11 — Browser-first account automation carries sensitive state.** [Playwright authentication guide](https://playwright.dev/python/docs/auth) explicitly warns that saved authenticated browser state can contain impersonation-ready cookies/tokens and should **never** be committed, even to a private repository. Browser-first is a comparison preference; rights to site automation, session use, observed UI, 2FA, privacy and resident RAM are separate gates. Authenticated browser automation on a turned-off laptop requires a separately online authorized host; local Jan/Chrome cannot work while hardware is powered down.

**F12 — Gmail API should not be dismissed as automatically paid, nor assumed available.** [Google Gmail current quota page](https://developers.google.com/workspace/gmail/api/reference/quota) shows `messages.get = 20`, `threads.get = 40`, daily billing threshold, and a 2026-05-01 quota-transition note. Official documentation says **standard Gmail API use has no additional charge**, with later 2026 excess usage billing plans; exact project cohort/region/OAuth/Restricted scopes are separate. Browser/connected-app path vs direct API must be compared on a specific actual workload and privacy/consent, not folklore. No API account or mailbox operation authorized.

**F13 — ChatGPT Plus custom-MCP bridge cannot be promised.** [OpenAI custom MCP help](https://help.openai.com/en/articles/12584461-connecting-custom-mcp-servers-in-chatgpt) currently documents custom connections for Pro read/fetch and full write-capable connections for qualifying Business/Enterprise/Edu; it does not establish a Plus user ability to create arbitrary custom MCP. Remote MCP/tunnel adds endpoint/entitlement/region/security gates. Installed first-party/third-party connectors are separate from custom user-local CAP-006 access. **Keep local independent conversational path as first deliverable**; available ChatGPT connected tools can still assist with repo/research as their own scoped path.

**F14 — An overlooked viable Windows-native alternative exists.** [.NET Generic Host](https://learn.microsoft.com/en-us/dotnet/core/extensions/generic-host) offers lifecycle, graceful stop, logging, dependency injection and background worker integration without an Agent framework. Compare a small C#/.NET app against Python stdlib + host GUI and existing ready app for control-plane reliability and maintenance; do not automatically choose Python because CAP-006 happens to be written in it. A cross-language subprocess/JSON contract may permit retaining CAP-006 regardless of host choice.

## 3. Architecture bundles compared (hypotheses, not benchmarks)

| Bundle | Boundary / components | Pros | Practical risk / reason to defer |
|---|---|---|---|
| **B0 — Built-in connectors or manual supervised chat** | available ChatGPT/GitHub/Gmail tools, no new local app | Zero new Windows runtime, helps immediate research/account reading where connector connected | Does not satisfy independent local offline assistant or Windows private-file tool access |
| **B1 — Capability-first local thin core (recommended FIRST COMPARISON)** | typed schema + policy + direct CAP-006 + one minimal chat UI; model optional; no resident scheduler | Small attack surface and low idle footprint hypothesis; easiest isolated tests | Host/UI/chat→tool reliability and actual Persian usability still unproven; custom code maintenance |
| **B2 — Ready local chat host + narrow stdio tool** | Jan Desktop conditional, fixed one tool and trusted executor | Ready chat experience and model tooling; avoids building UI | Exact installed Jan version, local model tool-call success, UI approvals and memory unknown; global autoapprove must stay OFF |
| **B3 — Browser-centered self-hosted ready workspace** | Open WebUI/alternative, HTTP/MCP server if required | Rich browser UI, integrations, future role features | Extra process/container/HTTP transport/network/RAM/privacy; native stdio not supported in Open WebUI's official MCP design |
| **B4 — Durable workflow-centric host** | DBOS or LangGraph or Dagu behind policy core | Retry/checkpoint/workflow GUI/approval features, future longer tasks | Extra dependencies/persistence semantics, Windows/SDK fit and replay/side effects; premature for one tool call |
| **B5 — Multi-Agent platform / router / full services** | Ruflo/AutoGen/CrewAI etc, full model router, separate DB, dashboard | Potential future many roles and concurrent jobs | No demonstrated incremental benefit on 8GiB device, high governance/performance complexity, broad tool surface. Defer |

**Conditional architecture recommendation:** choose B1 **as the simplest comparator**, with B2 and one B3/alternative UI as same-fixture competitors; do **not** mark B1 or any exact language/model/host as ADOPTED until G1 observations and S2 pilot/decision. Even if a ready-made B2 beats B1, retain the host-independent policy/tool contract.

## 4. Selection gates and benchmarking protocol

**Stage 0 — non-negotiable exclusion gates:** lawful access/region and licenses, privacy/consent, no unknown overage, no secrets in Git, default-deny at actual executor, reversible installation, supported Windows/Python/driver dependencies; fail/unknown means no activation, not zero score.

**Stage 1 — weighted comparative score AFTER exclusions (rubric is PROPOSAL):** correctness/real task value 25%; safety/policy+replay behavior 25%; idle/peak/post-unload RAM/CPU 20%; implementation+maintenance effort 15%; portability/extensibility 10%; documented cost/license 5%. Scores are not assigned without same-fixture evidence; users may change weights.

**Stage 2 — isolated tasks with one common fixture and negative tests:**
- T01 two permitted local Markdown files: Persian question→scoped CAP-006 real call→exact source/line/hashes; no terminal per ordinary user request.
- T02 blocked path traversal/symlink and unapproved broader file root; denied regardless of prompt trickery.
- T03 bad/unknown tool arguments, timeout/cancel and dead process; no orphan tools or claim of successful search.
- T04 mock Gmail/site corpus MAIL-P001: dedup, follow-up, false leads, conflicting date/budget, no network/send.
- T05 simulated approval/deny/expiration; a forged or replayed approval cannot authorize changed payload.
- T06 simulated crash between `attempted` and `confirmed`; return `UNKNOWN_OUTCOME` / reconcile, never blind duplicate send.
- T07 2–3 defined logical roles sequentially with shared model; same tasks compared to one assistant and to Agent candidate only on incremental value.
- T08 actual user-Windows resource sampling only after separate scope: OS available, model load, real workload, offload/unload, subprocess cleanup, cold/steady latency, idle footprint, battery/thermal where relevant.
- T09 disable network/close browser/power-off thought experiment; report true offline and always-on boundaries, not a simulated live cloud outcome.
- T10 same provenance/version mixed old CURRENT vs live canonical status; current evidence wins.

**Measurement:** frozen source SHA/fixture hash; model version/weights/quantization/context/tool template; SDK/OS versions; repeats, start/stop clock, number of manual steps, human-reviewed task-success numerator/denominator, unsafe calls (hard zero), false approvals, tokens only if exposed, peak+idle+post-unload RAM, recovery outcome, source fidelity and estimated recurring cost. Report N/A/UNKNOWN rather than fabricated speedup or percent; never compare baseline from historical time with a newer answer as if identical facts.

## 5. Where the new research materially changes the proposed master roadmap

1. **Move an explicit architecture bake-off before code**, selecting transport/host independently from model/inference/long-running workflow; G1 narrow GUI evidence is a sub-check, not entire product plan.
2. **Add a trusted approval/side-effect state-machine design from the start**, even when M1 is read-only; exercise mock idempotency prior to real send.
3. **Separate immediate lightweight log/receipt from future visual observability**; do not install telemetry infrastructure for first lookup.
4. **Place Gmail/mail and freelance opportunity copilot as first economically useful assistant**, while CAP-006 remains safest technical integration gate and shared knowledge service.
5. **Treat a specialist as a versioned logical role/profile, not a new process/model**; add role collaboration after utility proof, not before.
6. **Admit better ready-made solutions after verified comparison**; tools existing in user's environment have no ranking bias, architecture remains greenfield.
7. **Promote durable execution/resource manager only on failure/recovery or workflow thresholds**, using separate tests of process ownership, idempotent side effect and Windows resource accounting.
8. **Keep future RADAR, workflow pattern reuse, advanced model router and dashboard as discrete optional capabilities**, not mandatory construction milestones; research libraries remain ongoing but not blockers.
