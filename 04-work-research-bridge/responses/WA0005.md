## 1. Executive discovery

1. **A browser interface does not settle the mail transport or AI cost.** Newly found Multi-Inbox uses official Google/Microsoft APIs behind its browser side panel; EmailSignal reads webmail DOM but requires a Node sidecar and an OpenAI model. Miel's ordinary AI triage uses snippets rather than full bodies. Each can miss a different part of the actual requirement.
2. **A useful no-account synthetic comparison already exists.** Email Triage ships a deterministic demo, local browser UI and Windows launcher. This offers a much smaller research trial than installing a full autonomous framework. Its live OAuth configuration requests write-capable scopes; its demo suitability must not be mistaken for readiness to connect the user's real mailbox.
3. **Two new browser-local agents merit conditional inspection, not immediate trust.** OpenSidekick has inspectable site permission logic and an MIT license; WebBrain has separate Ask/Act/Dev modes and GPL-3.0-or-later source. Actual manifests nevertheless grant broad website/debugger access; WebBrain additionally requests cookies and other sensitive browser capabilities. UI approval prompts do not narrow the extension's installed browser authority.
4. **Gmail's May 2026 quota change matters, but does not make a small digest inherently paid.** Current Google documentation has a daily no-extra-charge threshold and higher costs for full-body retrieval than older examples. A reproducible small-workload calculation appears in §7. Account/developer access from Iran, data rules and OAuth maintenance remain separate gates.
5. **Remote free browser allowances exist; a qualified free unattended private copilot was not established.** Cloudflare Browser Run, Browserbase and Browserless publish renewable allowances. Steel's current Launch credit is one-time, overriding older “100 hours/month free” articles. Session lifetime, regional eligibility, source terms, credential custody, scheduling, state and model costs prevent promotion of any of these to an approved laptop-OFF solution.

Common assumptions rejected by this review: “browser-first means no API”; “open source includes free hosted AI”; “visible inbox scan covers historical full threads”; “a scheduler in an extension works after laptop shutdown”; “a draft-only UI implies a provider-enforced draft-only OAuth scope”; and “template title proves its real graph.”

### 7.3 OAuth and draft/send boundaries

[Google scope table](https://developers.google.com/workspace/gmail/api/auth/scopes) classifies gmail.readonly as Restricted. gmail.metadata lacks bodies. gmail.compose authorizes drafts **and sending**; gmail.modify also permits broader mutations. Consequently a “save draft” button is not a provider-enforced draft-only token. For V1, external sending should not be available; prepare reply text locally without requesting write scopes.

[Restricted-scope verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification) includes exceptions such as personal use and development/testing. [OAuth policy](https://developers.google.com/identity/protocols/oauth2/policies) describes personal use as unshared/fewer than100 personally known people; server storage/transmission and exception applicability still require exact review. No universal “any personal server is exempt” claim is made.

[OAuth token documentation](https://developers.google.com/identity/protocols/oauth2/) states External+Testing refresh tokens generally expire after7days when Gmail scopes are included. Personal-use exception to public verification is **not** immunity from token expiry/revocation. Authentication failure needs visible user reconsent, not repeated secret collection or bypass.

[Google Cloud billing-account documentation](https://docs.cloud.google.com/billing/docs/how-to/create-billing-account) lists restrictions involving Iran among some Cloud services. This is adverse evidence about developer/cloud access, **not proof consumer Gmail itself is forbidden** or that all Gmail API access has one regional policy. For this Iranian-resident user, own-project access/terms remain a separate gate; free quota does not establish lawful developer availability.

### 7.4 Incremental sync rather than repeated archive scans

[Google sync guidance](https://developers.google.com/workspace/gmail/api/guides/sync) describes initial bounded full sync, complete-format retrieval and partial sync using historyId. History can expire; a stale cursor404 requires resync. Commit cursor only after the intended page/delta has been processed safely. Missing pages, duplicates and rate failures must not silently turn into an empty “no opportunities” report.

[Push guidance](https://developers.google.com/workspace/gmail/api/guides/push) uses Cloud Pub/Sub and requires watch renewal at least every7days, recommending daily. Push notifications are changes, not complete message bodies. Pub/Sub/cloud prerequisites and billing differ from Gmail API itself. For a 12-hour private digest, periodic partial sync is a credible simpler competitor; push is not obligatory.

## 10. Failure, safety and state criteria for the future pilot

These are acceptance criteria derived from the requested scenario, not an implemented central framework:

- Keep original source identity: mailbox/account, message ID,thread ID,platform external ID,origin URL, observed timestamp/content version. Dedup by stable identifiers and explicit cross-source link; title similarity only suggests a match.
- Full input coverage receipt: pages/messages examined, collapsed/omitted bodies, attachment status, truncation, unread/historical range, last successful sync and error states. A missing attachment means UNKNOWN requirements, not “none.”
- Preserve source evidence separate from model analysis; budget/fee/currency/deadline/eligibility must cite original text. A crypto mention does not prove Iranian eligibility or payout viability.
- Data freshness: budget change makes a new observation; do not silently overwrite the old evidence or continue a stale proposal.
- MIME/HTML: strip executable content, block remote trackers unless separately authorized; attachment open/parse bounded and isolated. No public reporting of raw private mail.
- Origin/recipient checks outside prompts: domain allowlist,redirect recheck, exact account, no untrusted link-triggered cross-site reads. Mail/site instructions cannot grant tool permissions.
- First test has no send capability. Later approval binds account+recipient+thread+body+attachment hashes+expiry. Changed draft invalidates approval. LLM-supplied approved=true is never authority.
- Unknown send outcome: record pending/unknown and reconcile sent state/service receipt before retry. A client-generated idempotency key is not a guarantee the remote site deduplicates. No blind resend.
- Failed read: bounded retry/backoff when safe; auth/challenge asks user; quota stop reports deferred work; no new page/provider paid fallback. A partial digest explicitly lists omitted scope.
- Resume cursor advances only with correct stored result; crash before/after side effect distinguished. One small durable store/mechanism first, no speculative queue/service swarm.
- Measure browser baseline and incremental renderer/extension/backend/model separately. Use sequential tasks and bounded tabs/context; no numerical RAM success from publisher “lightweight.”
- Pure rules/keyword extraction and source-cited templates can give useful Persian reports without an additional resident LLM. Model language/tool-call quality needs the same synthetic corpus; no specific new model/weight/cloud selected.
- Browser-managed AI is not zero footprint: [Chrome built-in AI](https://developer.chrome.com/docs/ai/built-in) manages models locally. Exact current hardware/language eligibility for this laptop was not established; Multi-Inbox's Gemini Nano claim does not prove Persian/8GiB fit.
- Audit metadata only where possible: call/source IDs,status,cursor,counts,selected version,approval/receipt reference; redact credentials and private body. Log usefulness/failure, not create an additional authority.
