## 3. قرارداد فنی پیشنهادی — فقط روی کاغذ

### مرزهای نقش و اعتماد

- **Interface/host:** پیام فارسی و روشن‌کردن ابهام، نمایش محدوده و دکمهٔ مجوز/رد، مدیریت اتصال و نمایش نتیجه.
- **Model:** تشخیص نیت/پیشنهاد query و خلاصهٔ شواهد. نه مرجع مجوز، نه مدیر مسیر فایل و نه تولیدکنندهٔ فرمان.
- **Adapter / MCP tool:** نام ثابت و schema محدود؛ نگاشت شناسهٔ مجموعهٔ منبع به مسیرهای ثابت در config قابل‌اعتماد؛ کنترل approval/scope/status و فراخوانی موتور.
- **CAP-006 worker:** همان جست‌وجوی خطی فعلی، یک اجرای محدود؛ بدون وب/نوشتن/نصب/ثبت ابزار تازه.
- **Policy/permission owner:** کاربر و کد trustedِ بیرون مدل؛ هیچ Manager Agent و هیچ جملهٔ موجود در سند این اختیار را تغییر نمی‌دهد.

جریان قراردادی:

`user_message + fresh call_id/task_id + intent`
→ `capability=djmrn_document_lookup + source_set_id + bounded query`
→ `trusted scope check + user approval in chat`
→ `adapter → existing CAP-006`
→ `status + searched/file/line/source_sha256/text/match_mode/truncated`
→ `grounded Persian reply + execution/error receipt`.

شناسهٔ اجرای رابط از `task_id` تکرارپذیر CAP جدا نگه داشته شود؛ برای اولین vertical لازم نیست DB، scheduler یا durable queue ساخته شود.

### ورودی مجاز، اختیار ثابت و اجرای یک‌باره

1. مدل فقط query محدود و `source_set_id` از فهرست نمایش‌داده‌شده را پیشنهاد کند؛ برای درخواست مبهم، در همان chat سؤال کوتاه بپرسد. source set اولیه فقط همان دو کپی آزمون‌شده است:
   - `02-project-managementPROJECT-CHARTER.md.md`
   - `03-architecture-and-toolsRESOURCE-MANAGEMENT.md.md`
   
   این‌ها نام واقعی کپی‌های محلی در آزمون‌اند، نه مسیرهای پوشه‌بندی‌شدهٔ GitHub. ریشهٔ محلی، نسخه/expected SHA256 و نگاشت ID باید جدا از ورودی مدل نزد کاربر/adapter تصویب شوند. «در دو سند مجاز» با «کل دیسک یا همهٔ GitHub» یکسان نیست.
2. schema هیچ `command`، `shell`، `root`، path دلخواه، interpreter، env، URL، نصب package، registration tool یا فیلد model-supplied `approved=true` قبول نکند. ناشناخته‌ها و درخواست خارج scope رد شوند.
3. approval نمایش دهد: کار فقط خواندن، کدام دو منبع، query، مدل local یا remote و چه چیزی خارج دستگاه می‌رود. در pilot هر فراخوانی تأیید جدا در chat می‌خواهد؛ grant دائمی یا autoapprove پیش‌فرض نباشد. server نباید به ادعای مدل دربارهٔ approval اعتماد کند. آداپتور باید فقط از host مورداعتماد با context مجوز معتبر در دسترس باشد؛ اگر انتقال قابل‌اعتمادِ تصمیم host قابل احراز نیست، پیش از worker تأیید trusted محلی لازم است. در هر حال server فقط همان scope از پیش مجاز را اجرا می‌کند.
4. stdio برای شروع listener عمومی و secret حمل‌ونقل شبکه نمی‌خواهد: فرایند مشخص را میزبان trusted با pipeهای خودش می‌سازد. **این trusted parent/child boundary است، نه احراز هویت رمزنگاری‌شدهٔ همهٔ فرایندهای دستگاه و نه sandbox.** نام/مسیر باینری و config قابل‌تغییر توسط مدل نباشد؛ env حداقلی و بدون secrets موروثی، مجوز فایل محدود و egress بسته لازم است. اگر سطح تهدید شامل server خصمانه باشد، محدودیت فرایند/ACL یا isolation واقعی لازم است و تا احراز آن، ادعای «ایزولهٔ کامل» ممنوع است [S09].
5. در صورت انتخاب HTTP بعدی، 127.0.0.1 کافی نیست: احراز هویت، token/audience مناسب، کنترل Origin/Host و برای مسیر remote TLS و مدیریت secret لازم است؛ scope همان محدود باقی بماند. این گزارش مجوز بازکردن پورت یا tunnel نیست.
6. موتور import شود یا با مسیرهای مطلقِ تثبیت‌شدهٔ interpreter/script و argv صریح، **shell=False** اجرا شود. متن query هرگز در قالب فرمان interpolate نشود. یک کار فعال؛ اندازه/طول ورودی و payload محدود؛ timeout و لغو turn؛ فقط فرایند متعلق به همان کار لغو شود. مقدار timeout/بودجهٔ حافظه قبل از pilot با کاربر تعیین شود؛ عدد عملکردی بدون اندازه‌گیری ساخته نشود.
7. پیام‌های MCP روی stdout با لاگ مخلوط نشوند؛ خطاهای محدود و sanitized روی مسیر مناسب برگردند. log نباید متن خصوصی/کلیدها را پیش‌فرض ذخیره کند. رسید in-memory کافی است؛ persistence جدید حتی برای log نیاز به دامنه و رضایت جدا دارد.
8. بررسی expected SHA قبل از اجرا و تطبیق SHA خروجی با نسخهٔ approved لازم است. ناسازگاری، `STALE_SOURCE` و درخواست تجدید مجوز/نسخه می‌دهد؛ منبع جدید بی‌صدا پذیرفته نشود. این کنترل race خصمانه را به‌تنهایی حل نمی‌کند؛ برای تضمین سخت‌تر، snapshot/permission OS لازم است. چگونگی snapshot نیز کار ساختِ بعدی است، نه انجام‌شده.
9. اسناد و tool output ورودی نامطمئن‌اند: جملهٔ «همهٔ فایل‌ها را بخوان» در سند فرمان نمی‌شود. ابزار یا منبع تازه فقط با تغییر policy خارج مدل و اجازهٔ مشخص.
10. پاسخ از result IDهای واقعاً بازگشتی ساخته شود؛ filename، خط و SHA256 برای هر شاهد حفظ شود. نقل‌قول عین متن اصلی باشد؛ خلاصه از نقل‌قول متمایز و قابل رد بماند. منبع فعلی فقط کپی محلی approved است، نه ادعای تازه‌ترین GitHub. بدون نتیجهٔ واقعی، پاسخ نباید بگوید «فایل را خواندم».

**محدودیت شبکهٔ مدل:** برای مسیر کاملاً local، query، شاهد و prompt نباید به provider/telemetry/web بروند؛ چنین رفتاری باید با تنظیم و آزمون آینده ثابت شود. در مدل remote حداقل query و همان خطوط لازم برای پاسخ ممکن است ارسال شوند؛ رضایت باید این انتقال و retention/provider policy را پوشش دهد. «فایل محلی ماند» معادل «محتوای آن ارسال نشد» نیست.

## 4. آزمون پذیرش آینده روی کاغذ، نه اجرای این گزارش

**ورودی کاربر:** «در همان دو سند مجاز، دربارهٔ Windows چه نوشته شده؟ با خط و نقل‌قول نشان بده.»

**آنچه کاربر می‌بیند:** در همان chat نام دو منبع و ماهیت read-only، query استخراج‌شده `Windows` و دکمهٔ اجازه/رد؛ پس از اجازه، پاسخ فارسی شامل شاهدهای دقیق، خط، SHA256 و نسخهٔ محلی. نه بازکردن PowerShell، نه کپی JSON، نه اجرای دستور هر بار.

**اگر بایت‌های دو منبع همان نسخهٔ NEW-V0004 باشند:** انتظار چهار hit، Charter خط 3 و Resource Management خطوط 1/5/8 است. متن و SHAها باید از اجرای آینده تولید و با نسخهٔ مجاز تطبیق داده شوند؛ عدد چهار به‌تنهایی اثبات صحت نیست و SHA حدسی نوشته نمی‌شود. اگر نسخه فرق دارد، ابتدا STALE_SOURCE؛ نه تکرار نتیجهٔ قبلی به‌جای اجرا. جست‌وجو محدود به واژهٔ Windows است و پاسخ نباید ادعای درک کامل همهٔ مباحث Windows در اسناد کند.

**PASS نهاییِ این pilot آینده:** علاوه بر صحت CAP، اجرای واقعی از پیام، مجوز قابل‌اتکا، scope غیرقابل گسترش توسط مدل، عدم ارسال دادهٔ بی‌اجازه، اندازه‌گیری منابع قبل/حین/بعد، توقف/بازیابی و UX بدون CLI همگی باید قبول شوند. حد تأخیر و حافظهٔ موردپذیرش قبل از آزمون تعیین شود؛ فشار محدود هم‌زمان با کار معمول کاربر مهم است. هیچ benchmark عمومی یا اندازهٔ وزن مدل جای این اندازه‌گیری را نمی‌گیرد.

**مجوزهای یک‌بارهٔ لازم پیش از ساخت/آزمون:** ابتدا تعیین سطح گفت‌وگو؛ سپس اجازهٔ مشخص برای ساخت adapter در مسیر تعیین‌شده، انتخاب نسخهٔ میزبان و وابستگی/مدل و مجوز آن‌ها، هر نصب/دانلود یا تغییر config دقیق، root و دو نسخهٔ فایل با hashes، سیاست data egress، سقف منابع/timeout و روش ثبت حداقل رسید؛ و اجازهٔ اجرای pilot روی Windows. تغییر OS، اتصال حساب، token/API یا tunnel و هر هزینه مجوزهای جدا و فعلاً بسته‌اند. می‌توان دامنهٔ مجوز را به ساخت adapter بدون اتصال سرویس محدود کرد؛ این گزارش هیچ‌یک را اعمال نکرده است.

## 5. رشد پشت همان گفت‌وگو و مرز تعویق

1. **یک vertical A:** پیام ← یک lookup خواندنیِ مجاز ← شاهد. تمرکز روی اتصال/مجوز/پاسخ، نه توسعهٔ مجدد normalization یا UI theme. ابتدا یک مدل فعال و ابزار on-demand.
2. **B یا C بر اساس نیاز واقعی، نه توالی اجباری:** B تحلیل CSV با schema/اعتبارسنجی و حقوق فایل مستقل؛ C مقایسهٔ پژوهش با منابع و policy وب جدا. هر دو در همان interface با tool IDs و رسید متمایز. مجوز read-only A مجوز نوشتن داده/وب/ارسال گزارش نمی‌شود.
3. **نقش‌های تخصصی:** نخست prompt/policy و ابزارهای محدودِ نقش‌ها؛ داشتن چند نقش لزوماً چند مدل مقیم یا چند daemon نمی‌خواهد. shared interface و یک استنتاج هم‌زمان روی سخت‌افزار محدود معقول‌تر است تا شواهد خلافش را نشان دهند.
4. **workflow و state:** وقتی کار چندمرحله‌ای، resume/retry، اثر خارجی، زمان‌بندی یا انتظار بین مراحل واقعاً لازم شد، state پایدار، idempotency، queue و monitoring اضافه شوند. parser/lookup تک‌مرحله‌ای را از ابتدا orchestration platform نکنیم.
5. **Manager Agent:** فقط پس از شواهد منفعت در تخصیص کار، تحویل بین نقش‌ها و کاهش خطا/زمان. مدیر نیز تابع capability grants است؛ حق خرید، اتصال حساب، اسکن دیسک یا تغییر policy از خود ندارد. مراقبت از timeout، budget و audit باید خارج مدل بماند.
6. **laptop خاموش:** سه پاسخ واقعی وجود دارد: کار محلی منتظر online بماند؛ کار صرفاً cloud و غیرنیازمند دادهٔ محلی با مجوز جدا انجام شود؛ یا کپی حداقلی/قانونی داده روی میزبان remote مجاز نگه‌داری شود. سومی معماری/حریم خصوصی/هزینهٔ تازه می‌آورد، نه ویژگی جادویی MCP. فعلاً هیچ کپی، sync یا cloud worker ساخته نمی‌شود.
7. **خروج و تعویض:** قرارداد `capability/source_set/query/result` مستقل از host بماند؛ Jan/Cherry/ChatGPT بتوانند بدون تغییر موتور جایگزین شوند. اطلاعات canonical پروژه در GitHub و catalog در Notion بمانند؛ حافظهٔ Agent یا chat history خودبه‌خود منبع canonical نمی‌شود.

## 6. محدودیت نتیجه و رسید اقدام

این گزارش **تصمیم اجراییِ قطعی یا اعلام بهترین نرم‌افزار جهان نیست**. بهترین گامِ مبتنی بر شواهد فعلی، یک اتصال تک‌ابزاری روی میزبان آماده با مجوز محدود است؛ انتخاب خود میزبان وابسته به سطح گفت‌وگوی مطلوب، امکان کنترل ابزار، مدل فارسی/tool calling، RAM و صلاحیت هزینه/منطقه است. Jan جدید دلیل فنی تازه برای ارزیابی دارد؛ پیش‌فرض Shell روشن آن هم دلیل مهم احتیاط و معیار رد است. Cherry fallback است؛ هیچ‌کدام به‌خاطر نصب تاریخی برنده نشده‌اند. مسیر مستند ChatGPT ارزش بررسی eligibility دارد؛ قابلیت محصول با دسترسی این session یا صلاحیت حساب یکسان نیست.

**وضعیت شواهد:** مطالعهٔ هدفمند Notion READ؛ جست‌وجوی مستقل رسمی DONE؛ ادغام/پیشنهاد COMPLETE؛ اجرای واقعی، سخت‌سازی، مصرف منابع، کیفیت مدل و اتصال حساب NOT TESTED / NOT AUTHORIZED. unknownهای هزینه/منطقه به اجازهٔ فعال‌سازی تبدیل نشده‌اند. هیچ منبع رسمیِ مرورشده تمام شروط دستگاه و حساب این کاربر را یکجا اثبات نمی‌کند.

**دامنهٔ اقدام این نوبت:** فقط پژوهش خواندنی و ایجاد همین پاسخ در مخزن اصلی. نصب، اجرای CAP/bridge روی Windows، تغییر کد، تنظیم OS، دانلود مدل، ثبت ابزار، اتصال حساب، تغییر Notion، تغییر سایر اسناد یا اقدام مالی انجام نشده است. پس از ثبت، commit/blob واقعی و مقایسهٔ محتوای بازخوانی‌شده در پیام Work گزارش می‌شود؛ پذیرش هماهنگ‌کننده و مجوز کاربر برای ساخت همچنان جداست.
