# KYNXA H3 — Park the candidate until zero-routine-manual-operation is demonstrated

**Date:** 2026-10-22. **Decision scope:** user states they do not want complex multi-engine setup or recurring manual PowerShell. KYNXA is acceptable **only if the model-engine connection can be automated permanently with no normal daily manual setup**. This is a bounded operational evaluation/STOP condition, **not a decision to uninstall** and **not global architecture selection**.

## Observed evidence inherited from H2/H3
- KYNXA Windows 1.7.0 installed, GUI starts, six chat model weights in local catalog (5 external GGUFs imported by reference, 1 KYNXA-managed Qwen 3 4B), two auxiliary vision projectors and one Jan embedding excluded. No successful KYNXA model text generation proven.
- Actual KYNXA native Gemma 3 1B runtime state `waiting-resource`, only this native model enabled, no llama-server PID, due to likely resource-admission cap with OS-visible 5.88 GiB RAM, 1.64–2.59 GiB available across user samples. Engine and bytes intact; no proof model file corrupted.
- Jan OpenAI-compatible connection `DJMRN - Jan Local` saved in KYNXA on loopback `127.0.0.1:1337/v1`; user screenshot of Chat showed "Generating" with no textual answer and a prior "Generation stopped"; no Jan API-direct success receipt. Thus configuring an address != operational hands-free inference.
- Ollama via PowerShell GGUF create / one-shot chat and a direct bundled KYNXA llama-server loopback experiment were **offered as proposals only**; no user run results or working daemon startup were reported. Do not treat them as already set up.
- Tagged KYNXA source v1.7.0 does not expose verified supported one-click disabling of resource admission; stopping its resource service would break native managed inference rather than solve it. Bypassing it via third-party/local direct HTTP engine would require automatic lifecycle management.

## Decision/status and criteria
- **Recommendation to user:** **PARK/HOLD KYNXA**, leave installation and original model weights in place, no removal or extra downloads now. Return to primary DJMRN chat-first assistant work. Evaluate second queued candidate `goose` or current lightweight installed host separately against requirements; not automatically selected/installed. Do not continue repeated RAM PowerShell probing and manual Jan/Ollama/UI detours.
- Revisit KYNXA only with an end-to-end verified, minimal-footprint solution: **one-time reproducible setup**; Windows user startup automatically starts the local engine on loopback; automatic availability/health-check/recovery; KYNXA connection persists; clean shutdown; no routine PowerShell or manual click; single-model RAM limit and no hidden payments/accounts; user can disable/rollback; basic Persian chat benchmark and approval-bound tools test. A Windows Task Scheduler/startup-script + local API is technically feasible in principle, but **no real recipe has been validated on this machine**; RAM constraints could still prevent operation. Do not announce it as an existing capability.
- No device/system changes by coordinator. KYNXA is not judged categorically insecure or incompatible, only currently too costly in operational friction and **H3 not passing**. No G3B file access guard opened and no G3B or CAP-006 state changed. D-005 overall host decision OPEN.
