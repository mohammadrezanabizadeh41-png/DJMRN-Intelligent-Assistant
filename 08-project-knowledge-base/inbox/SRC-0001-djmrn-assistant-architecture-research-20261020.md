# پژوهش معماری دستیار هوشمند DJMRN

۲۰ اکتبر ۲۰۲۶ | Windows 11 | معماری محلی، هیبریدی و مستقل از Agent

## ۱. کشف مهم شما درست است؛ حتی امکانات بیشتری هم وجود دارد

برای ساخت یک سیستم هوشمند کاربردی، الزاماً نیازی نیست از ابتدا LLM، موتور استنتاج یا Agent داشته باشیم.

می‌توانیم ابتدا یک سیستم مستقل بسازیم که داده‌ها را دریافت، ذخیره، جست‌وجو، مرتب، مقایسه و پردازش کند؛ کارها را زمان‌بندی کند؛ با نرم‌افزارها ارتباط برقرار کند و وضعیت اجرای عملیات را نگه دارد.

سپس به‌اندازهٔ نیاز، یک مدل هوش مصنوعی را به این سیستم اضافه کنیم؛ نه اینکه کل سیستم را بر مبنای حضور دائمی مدل طراحی کنیم.

این تفاوت بسیار مهم است:

- سیستم عادی نرم‌افزاری: وظایف مشخص را با قواعد و برنامه‌های معمولی انجام می‌دهد.
- سیستم مبتنی بر یادگیری ماشین: می‌تواند برای طبقه‌بندی، تشخیص الگو و پیش‌بینی از مدل‌های تخصصی کوچک استفاده کند.
- سیستم مجهز به LLM: در زمان نیاز از مدل زبانی برای فهم متن، استدلال، تولید پاسخ یا تصمیم‌های پیشنهادی استفاده می‌کند.
- سیستم Agentic: مدل در چارچوب اختیارات و محدودیت‌های مشخص، می‌تواند ابزار انتخاب کند، نتایج را بررسی کند و چند مرحله را پیش ببرد.

این چهار حالت می‌توانند مستقل یا مکمل باشند.

### یک اصلاح اصطلاحی مهم

Python یک زبان برنامه‌نویسی است، نه مدل هوش مصنوعی یا مدل زبانی.

همین‌طور Go، Rust، C# و JavaScript زبان برنامه‌نویسی‌اند. در مقابل، Qwen، Gemma و Llama خانواده‌های مدل‌های هوش مصنوعی هستند.

از طرف دیگر، SQLite پایگاه داده، ONNX Runtime موتور اجرای مدل و LangChain چارچوب توسعهٔ برنامه‌های مبتنی بر مدل است.

بنابراین به‌جای اینکه بپرسیم «کدام مدل جایگزین Python است؟» باید چند انتخاب مستقل داشته باشیم:

زبان برنامه‌نویسی + روش اجرای کارها + مدیریت داده + ابزارهای تخصصی + هوش مصنوعی اختیاری.

این جداسازی اجازه می‌دهد بعدها هر بخش را بدون بازسازی کل سیستم تغییر دهیم.

## ۴. انواع معماری‌هایی که می‌توانیم بسازیم

اینجا موضوع فقط انتخاب زبان نیست. می‌توانیم کل ساختار سیستم را به شیوه‌های متفاوت طراحی کنیم.

معماری A — Rule-Based Automation

یک قانون می‌گوید اگر رویداد مشخصی رخ داد، عمل مشخصی اجرا شود. مثلاً اگر فایل جدید آمد، قالبش بررسی، اطلاعاتش استخراج و در پایگاه داده ذخیره شود.

به مدل زبانی نیاز ندارد. برای کارهای قطعی، نقطهٔ شروع ساده‌ای است.

معماری B — Data-Centric / Database-First

نقطهٔ مرکزی سیستم، دادهٔ ساختاریافته، فایل‌ها و تاریخچهٔ معتبر است؛ نه مکالمه با مدل.

عملیات دریافت، جست‌وجو، تحلیل و به‌روزرسانی داده را نرم‌افزار انجام می‌دهد. LLM می‌تواند بعدها روی داده‌های مجاز پرسش پاسخ دهد یا تحلیل پیشنهادی تولید کند.

معماری C — Modular Monolith / Capability-Based

یک برنامهٔ مدیریتی داریم با قابلیت‌های داخلی قابل تفکیک: جست‌وجو، دریافت اطلاعات، مدیریت فایل، زمان‌بندی و تحلیل.

قابلیت‌های تخصصی پشت قراردادهای مشخص قرار می‌گیرند و فقط در صورت ضرورت به پردازه یا سرویس مستقل تبدیل می‌شوند. این روش با توسعهٔ تدریجی سازگار است.

معماری D — Event-Driven / Workflow

رویدادهایی مانند «ایمیل جدید»، «تغییر فایل» یا «زمان بررسی منبع» کار را آغاز می‌کنند.

موتور Workflow ترتیب اجرا و وضعیت مراحل را مدیریت می‌کند؛ بعضی مراحل کد معمولی‌اند و بعضی می‌توانند فراخوانی مدل باشند. حفظ وضعیت پس از خرابی باید جداگانه طراحی یا از ابزار آماده تأمین شود.

معماری E — Classical ML + Deterministic Software

طبقه‌بندی موضوعات، شناسایی الگو و تشخیص نوع محتوا با مدل‌های تخصصی کوچک انجام می‌شود.

برنامهٔ معمولی کنترل و اجرای کار را برعهده دارد. نه چت‌بات لازم است، نه Agent و نه الزاماً مدل مولد.

معماری F — Hybrid AI / LLM-on-Demand

نرم‌افزار معمولی مسیر پیش‌فرض است. تنها وقتی ابهام، فهم متن آزاد یا تولید محتوای پیچیده مطرح شود، مدل محلی یا سرویس مجاز آنلاین فراخوانی می‌شود.

این معماری می‌تواند بدون Agent Framework هم کار کند: برنامه داده را برای مدل می‌فرستد، پاسخ ساختاریافته می‌گیرد و آن را اعتبارسنجی می‌کند.

معماری G — Agent as Supervisor / Agent as Worker

Agent به‌جای اجرای دائمی تمام عملیات، نقش ناظر، تحلیلگر یا Worker قابل فراخوانی را دارد.

می‌تواند خروجی ابزارهای مختلف را تفسیر کند و برای اقدام بعدی پیشنهاد دهد؛ ولی اجازهٔ اجرای کارهای حساس از لایهٔ مجوز مستقل می‌آید.

این معماری‌ها کاملاً متضاد نیستند. مثلاً B + C + D + F می‌تواند یک سیستم داده‌محور با ساختار ماژولار، رویدادهای قابل بازیابی و هوش مصنوعی درخواستی بسازد.

برای لپ‌تاپ شما، این یک ترکیب ارزشمند برای مقایسه است؛ نه حکم قطعی به انتخاب آن.

## ۱۰. سه ترکیب معماری که برای دستگاه شما ارزش مقایسهٔ جدی دارند

ترکیب اول — Windows Native

کمترین وابستگی خارجی

Task Scheduler + PowerShell/C# + فایل یا پایگاه دادهٔ سبک + مدل اختیاری

مزیت: اتکا به قابلیت‌های بومی Windows و امکان اجرای کارهای مشخص بدون میزبان سنگین.

ضعف: قابلیت‌های پردازش پیشرفتهٔ متن و اتصال به ابزارهای متنوع ممکن است به اجزای اضافی نیاز داشته باشد.

ترکیب دوم — Lightweight Modular Core

Python یا Go یا C# + SQLite/Files + Workerهای درخواستی + مدل اختیاری

مزیت: کنترل روشن‌تر بر وضعیت، حافظه، مجوزها و بازیابی؛ امکان استفاده از زبان‌های متفاوت در اجزای لازم.

ضعف: بخشی از منطق اجرایی باید ساخته و آزمایش شود. اگر نیاز بسیار ساده باشد، این ساخت هم اضافی است.

ترکیب سوم — Workflow-First Hybrid

n8n یا Activepieces یا محصول مشابه + اتصال به ابزارهای تخصصی + LLM درخواستی

مزیت: طراحی و مشاهدهٔ مراحل کار آسان‌تر و اتصالات آمادهٔ بیشتری در دسترس است.

ضعف: مصرف منابع میزبان، وابستگی به محصول، محدودیت‌های نسخهٔ رایگان و پیچیدگی نگهداری باید بررسی شود.

این سه گزینه را می‌توان در آینده با ورودی یکسان مقایسه کرد: دریافت یک رویداد، استخراج اطلاعات، ذخیرهٔ وضعیت، توقف در زمان کمبود RAM، ادامه پس از راه‌اندازی مجدد و انجام یک تحلیل اختیاری با مدل.

برای انتخاب واقعی، معیارهایی مانند RAM اوج، زمان شروع، زمان پردازش، حجم دیسک، تعداد پردازه‌ها، کیفیت خروجی، بازیابی پس از خرابی و هزینهٔ نگهداری لازم است.

## ۱۱. تفاوت معماری محلی و هیبریدی

هیبریدی بودن فقط به این معنا نیست که «مدل کوچک روی لپ‌تاپ و مدل بزرگ در ابر» داشته باشیم.

می‌توانیم هر وظیفه را مستقل مکان‌یابی کنیم.

| قابلیت                            | اجرای محلی                        | اجرای آنلاین/هیبریدی            |
| --------------------------------- | --------------------------------- | ------------------------------- |

محدودیت سخت‌افزار لپ‌تاپ فقط برای بخشی تعیین‌کننده است که واقعاً روی آن اجرا می‌شود.

از طرفی استفاده از سرویس ابری باید از نظر سهمیهٔ رایگان واقعی، نیاز به کارت، اضافه‌مصرف، شرایط استفاده از ایران، حریم خصوصی و مجوز تجاری بررسی شود. در این پژوهش هیچ سرویس پولی یا اعتبار مصرفی به‌عنوان زیرساخت تصویب نشده است.

با بررسی اسناد زندهٔ Notion و وضعیت مخزن اختصاصی [DJMRN-Intelligent-Assistant](https://github.com/mohammadrezanabizadeh41-png/DJMRN-Intelligent-Assistant?utm_source=chatgpt.com)، این پژوهش با وضعیت فعلی پروژه سازگار است. پروژه هنوز در مرحلهٔ مقایسه و انتخاب فناوری قرار دارد؛ مخزن مستقل پژوهش کاربردی نیز دست‌نخورده باقی مانده است.

### جمع‌بندی معماری

به‌جای اینکه ابتدا یک Agent بسازیم و بعد تمام کارها را به آن واگذار کنیم، می‌توانیم ابتدا قابلیت‌ها و داده‌های قابل اعتماد بسازیم و هوش مصنوعی را به آن‌ها متصل کنیم.

حتی لازم نیست از همان روز اول مدیر سیستم یک سرویس دائمی باشد؛ شاید مجموعه‌ای از برنامه‌های کوچک که با رویداد اجرا می‌شوند، پاسخ بهتری بدهند.

جهت پژوهشی که بر اساس یافته‌های فعلی ارزش ادامه دارد، این است:

Data-first + Deterministic-first + Model-on-demand + Agent-when-justified

این یک اصل قابل بررسی است، نه نام یک چارچوب یا انتخاب قطعی پشتهٔ فنی.

برای پژوهش تخصصی بعدی، مهم‌ترین سؤال دیگر «بهترین Agent چیست؟» نیست، بلکه این است:

«کدام پایهٔ نرم‌افزاری یا محصول آماده می‌تواند با کمترین مصرف منابع، مدیریت داده و وظایف را به‌صورت مستقل انجام دهد و بعدها بدون بازنویسی اساسی به مدل‌ها و Agentهای مختلف متصل شود؟»

این سؤال باید در سه مسیر مستقل آزمایش شود: سیستم بومی Windows، میزبان ماژولار سبک و موتور Workflow آماده. در هر مسیر هم امکان استفاده از Python، Go، C# و سایر زبان‌ها بدون پیش‌فرض قبلی بررسی شود.

فعلاً هیچ نصب، تغییر سیستم، ثبت معماری یا اقدام عملیاتی انجام نشده است.
